# KManager 兼容性优先全面优化设计

## 1. 目标

在不改变 KManager 现有产品定位、用户操作路径和账号切换行为的前提下，系统性优化数据可靠性、登录态快照事务、代码结构、错误处理、安全边界、前端一致性、测试能力以及构建发布流程。

本轮主线优化面向下一正式版本 `v2.0.1`。主线优化必须做到：升级后原有账号、分组、头像、区服、登录态快照和旧版兼容路径仍可使用；正常用户不需要重新创建账号或重新配置应用。

## 2. 不属于主线的内容

以下项目风险较高，必须放入独立实验，不得由实施模型顺手加入主线：

- 不改变当前跨区切换依赖的 `Account`、`BrowserCaches`、`Cache`、`CachedData.db` 和注册表快照集合。
- 不改变“等待 Battle.net 正常退出后再采集/恢复”的流程，不重新采用强杀客户端方案。
- 不启用固定 24 小时快照过期规则。
- 不更换 WebView2 宿主技术，不把 bridge 全面重写成新的通信框架。
- 不改变当前非透明 WPF 宿主、固定窗口尺寸、禁用 GPU 的兼容性策略。
- 不加入云同步、遥测、账号密码存储或数据上传。
- 不把 `Data` 目录制作成可分享、可导出的普通备份包。

登录态快照瘦身、快照加密和 GPU/渲染策略分别建立实验计划。只有在独立测试版完成国服、亚服、美服、欧服及旧账号回归后，才能决定是否进入正式版本。

## 3. 不可回归约束

- 保留账号卡片、三点菜单、右键菜单、编辑、删除、更新登录状态、移动分组和拖拽跨组移动。
- 保留默认分组、创建/重命名/删除分组、展开/折叠、Active 计算和折叠组不渲染卡片的规则。
- 保留旧账号未标记区服时的旧版登录路径及补全信息引导。
- 保留“基础账号可以保存，完整登录态失败只作为增强失败”的规则。
- 保留同区快速切换和跨区完整快照切换现有判断逻辑。
- 保留 Battle.net 原本打开时，保存/更新完成后自动重新打开的体验。
- 保留 `%LOCALAPPDATA%\KManager\Data` 和 `%LOCALAPPDATA%\KManager\WebView2Cache` 路径。
- 旧数据迁移不得删除源目录，不得覆盖正式版独有账号，不得把损坏或不完整复制标记为迁移成功。
- 保留单实例、唤起已有窗口、托盘隐藏、最小化、开机启动和 WebView2 Runtime 修复流程。
- 测试版继续使用独立应用身份和独立数据目录，文件夹交付，不生成 zip，只保留最新测试版。

## 4. 总体实施策略

采用“先建立安全网，再改变内部结构”的渐进方案。每个阶段必须独立构建、独立测试、独立提交；后续阶段不得依赖尚未验证的实验性行为。

顺序固定为：

1. 建立测试工程、路径注入和非敏感诊断日志。
2. 将账号、分组、迁移状态改成可靠的原子存储。
3. 修复迁移和快照操作中的非事务行为。
4. 在保持 bridge 方法签名不变的情况下拆分 `BattleNetCore`。
5. 统一 bridge 错误结果和前端错误展示。
6. 处理前端无感性能、交互一致性和可访问性问题。
7. 加固 WebView2 导航和本地敏感数据边界。
8. 建立持续集成、发布验证和 `v2.0.1` 交付流程。

任一阶段验证失败时，只回退该阶段，不继续堆叠后续修改。

## 5. 目标代码结构

现有 `BattleNetCore.cs` 保留为对外编排入口，`WebBridge` 的公开方法名称和参数保持不变。逐步抽取以下职责：

```text
KManager-Client/
  Core/
    BattleNetCore.cs                 对外编排与兼容入口
    BattleNetCore.Constants.cs       区服与注册表常量
    BattleNetModels.cs               现有 bridge 数据模型
    Results.cs                       稳定错误码和操作结果
  Infrastructure/
    AppPaths.cs                      所有应用、Battle.net、测试路径
    AtomicFileStore.cs               原子文本/JSON写入与备份恢复
    AppLogger.cs                      不记录敏感值的滚动日志
  Data/
    AccountRepository.cs             accounts.json 读取、规范化、保存
    GroupRepository.cs               groups.json 读取、规范化、保存
    MigrationStateRepository.cs      迁移日志读取和保存
    LegacyMigrationService.cs        旧版/beta 数据发现、验证、合并
  BattleNet/
    BattleNetProcessService.cs       检测、正常关闭、稳定退出、启动
    BattleNetConfigService.cs        配置识别、复制、登录页配置
    RegistryStateService.cs          注册表采集、清理、恢复
    SessionSnapshotService.cs        Candidate/Current/Backup 事务
  WebBridge.cs                       COM bridge 适配，不放业务逻辑

KManager-Client.Tests/
  Data/
  Migration/
  BattleNet/
  Bridge/
```

拆分按职责进行，不以“减少行数”为目标。每抽取一个服务，先用特征测试锁定旧行为，再移动代码；禁止一次性搬空 `BattleNetCore.cs`。

## 6. 阶段一：测试基础与可诊断性

### 改动

- 新建 `KManager-Client.Tests`，使用 xUnit。
- 引入 `AppPaths`，生产环境仍返回当前固定路径；测试可以传入临时根目录。
- 文件系统、进程和注册表逻辑通过小型接口隔离，单元测试不得操作真实 Battle.net 数据或真实用户注册表。
- 新增 `%LOCALAPPDATA%\KManager\Logs\kmanager.log`，按大小滚动并只保留少量日志。
- 日志只记录阶段、耗时、文件数量、字节数、错误码和异常类型；不得记录注册表值、Token、Cookie、BattleTag、头像内容或完整账号 ID。

### 首批测试

- 旧账号缺少 `GroupId` 时进入 `default`。
- 默认分组不可删除；删除其他分组时账号回默认分组。
- 未标记区服账号仍走旧版路径。
- 完整登录态采集失败时账号基础信息仍保存。
- 客户端未稳定退出时不替换配置、不恢复快照、不更新 Active。
- 同区和跨区判断覆盖四个区服与未标记状态。
- 已完成迁移的源目录不会再次导入。

### 用户体验影响

正常界面和操作完全不变。仅新增本地诊断日志，方便定位用户机器上的迁移、WebView2、进程退出和快照失败。

## 7. 阶段二：账号、分组和迁移状态可靠存储

### 原子写入

`accounts.json`、`groups.json` 和 `migration-state.json` 统一采用：

1. 序列化到同目录临时文件。
2. 刷新文件内容到磁盘。
3. 旧文件存在时用原子替换并保留 `.bak`。
4. 首次写入时用同卷移动替换。
5. 启动读取主文件失败时尝试 `.bak`；恢复成功后记录日志并提示用户“已从备份恢复”。
6. 主文件和备份都损坏时返回显式错误，禁止静默返回空账号列表。

### 并发保护

- 对账号、分组和迁移状态分别使用进程内 `SemaphoreSlim`。
- 复合操作按照固定锁顺序执行，避免编辑信息和移动分组互相覆盖。
- bridge 在同一操作未结束前返回 `operation_in_progress`，前端保持当前按钮禁用逻辑。

### 用户体验影响

正常操作无变化。发生磁盘错误、断电或文件损坏时，用户会看到可理解的恢复/失败提示，不再误以为所有账号消失。

## 8. 阶段三：迁移流程事务化

### 迁移状态

每个来源目录记录 `Pending`、`InProgress`、`Completed` 或 `Failed`，同时保存来源规范化路径、导入模式、开始/完成时间、文件数、字节数和稳定错误码。

只有以下条件全部成立才能写入 `Completed`：

- 元数据合并已成功写入。
- 每个新增/覆盖账号已先复制到 staging 目录。
- staging 中至少存在合法的 `Battle.net.config`。
- 需要导入的当前 `BattleNetSessionState` 已完成结构验证。
- staging 已通过目录重命名提交到正式账号目录。

### 迁移规则

- 源目录只读，不删除、不改名。
- 正式版独有账号保留。
- beta 同 ID 元数据继续优先，但只在对应账号目录 staging 成功后提交。
- `BattleNetSessionStateCandidate` 不导入。
- `BattleNetSessionStateBackup` 默认不导入正式 Current；先通过测试确认它不参与正常切换，再在兼容测试通过后排除。若测试不充分，则保持复制，不能为了节省空间擅自删除。
- 迁移前统计所需空间；空间明显不足时停止迁移并显示需要空间，不进入半复制状态。
- 前端显示迁移阶段、已处理账号数和可取消的“稍后重试”；取消只停止未提交账号，不回滚已完整提交账号。

### 用户体验影响

首次升级会多出明确进度和错误说明。正常升级结果不变；失败时旧数据仍完整保留，可重新尝试。

## 9. 阶段四：登录态快照事务与进程控制

### 进程控制

- 抽取 `BattleNetProcessService`，保持“请求正常关闭、确认客户端消失并稳定 3 秒、最多等待 30 秒、之后才处理 Agent”的现有行为。
- 同区旧版快速路径暂不改变，以特征测试锁定当前行为。
- 所有等待使用条件检测，不增加新的固定大延迟。
- `LaunchBattleNet` 返回明确结果，找不到安装路径或启动失败时通知前端，不再静默吞掉。

### 快照事务

快照更新顺序固定为：

1. 清理上次遗留的 Candidate。
2. 将新状态写入 Candidate。
3. 验证 metadata、注册表记录和必要本地状态。
4. 将当前 Current 移到临时 Backup。
5. 将 Candidate 移到 Current。
6. 提交对应 `Battle.net.config.candidate`。
7. 全部成功后删除临时 Backup。
8. 任一步失败时恢复旧 Current 和旧配置，并返回具体错误码。

`BackupAndDeleteDirectory` 必须改为：备份复制及验证成功后才删除源目录。复制失败时立即终止，绝不继续删除。

恢复快照时返回 `SnapshotRestoreResult`，至少区分：缺少快照、注册表恢复失败、本地目录恢复失败、配置提交失败和 Battle.net 启动失败。部分恢复不得报告成功，也不得提前更新 `LastUsed`。

### 用户体验影响

成功路径保持不变。以前可能静默留下坏状态的场景会改成明确失败并保留旧状态；这属于安全性改善，而不是功能退化。

## 10. 阶段五：Bridge 和前端契约

### Bridge

- 保留当前公开方法，先增加详细结果方法；旧布尔方法继续作为兼容包装。
- 统一 `OperationResult`：`Success`、`Code`、`MessageKey`、`Recoverable`，不把异常文本直接暴露给前端。
- `IsCoreReady` 改为返回初始化状态：`starting`、`migrating`、`ready`、`failed`，并提供只含安全信息的进度。
- 使用显式 COM 接口代替 `ClassInterfaceType.AutoDual`，仅暴露 UI 真正需要的方法。
- WebView2 导航只允许 `http://app.local/`；外部链接继续通过受限的 `OpenExternalUrl` 打开系统浏览器。

### 前端

- `loadData` 读取失败必须向上抛出，显示“重试/打开日志目录”错误页，不能捕获后展示空账号页面。
- 创建和重命名分组改为应用内输入弹窗，移除 `window.prompt/alert`。
- 开机启动改为后端返回成功/失败；失败时恢复开关状态。
- 旧 localStorage 头像只在展开组的可见账号中懒加载；后端已有头像时不再读取 localStorage。
- 删除多余的 150ms 删除延迟；剪贴板、打开链接和登录新号补齐失败提示。
- 保持现有布局、配色、卡片、动画和帮助内容，不进行视觉重做。

### 用户体验影响

界面外观基本不变。错误提示、分组输入和开机启动反馈更一致；旧头像仍可显示。

## 11. 阶段六：安全与隐私

- 启动时确保 Data、Logs、备份目录不授予普通其他用户额外写权限；不破坏当前用户和管理员访问。
- 日志、错误信息和迁移状态禁止写入认证数据。
- README、首次指南和 Data 目录说明继续明确“Data 可能包含有效登录态，不要分享”。
- 安装目录、`app.local` 和 bridge 边界按最小权限处理。
- 正式应用和最终安装包预留 Authenticode 签名步骤；没有证书时可以构建本地测试产物，但发布检查必须明确报告 `NotSigned`，不能把发布者元数据当作签名。
- 完整快照加密不进入主线。原因是跨区切换需要频繁恢复大量文件，直接加密可能显著增加时间和失败面；另建实验评估 DPAPI 保护密钥、兼容旧数据和灾难恢复。

### 用户体验影响

正常使用无变化。签名完成后 SmartScreen/未知发布者体验改善；没有证书时不会伪装为已签名。

## 12. 阶段七：工程结构、依赖与发布

### 结构和测试

- 每次只抽取一个服务，原 bridge 契约保持不变。
- 为迁移、账号数据、快照提交、进程退出和错误码建立自动测试。
- 增加包含大量小文件的迁移性能测试，但使用测试临时目录，不复制真实 Data。
- 手动回归矩阵必须覆盖：全新安装、v1 升级、beta 升级、已有 v2 数据、损坏 JSON、磁盘空间不足、Battle.net 无法退出、无完整快照、四区服切换和旧未标记账号。

### 持续集成

- Windows CI 执行 `npm ci`、`npm run lint`、`npm run build`、C# 测试和 Release 构建。
- 前端构建后比较 `KManager-UI/out` 与 `KManager-Client/wwwroot`，不同则失败，防止发布旧静态资源。
- NuGet 漏洞检查和 npm audit 作为报告；不得自动运行 `npm audit fix --force`。
- 增加发布验证脚本：检查 C#、前端、安装器版本一致；检查应用和安装包签名状态；生成 SHA-256；验证安装包和绿色版包含相同业务资源。

### 发布

- 下一正式版本使用 `v2.0.1`，不再覆盖 `v2.0`。
- 先生成独立测试文件夹并完成回归，再发布安装包和绿色版。
- 发布前更新 `README.md`、`CHANGELOG.md`、`PROJECT_CONTEXT.md`、包版本、程序集版本和 Inno Setup 版本。
- 发布后核对 `main`、tag、GitHub Release、两份附件、本地文件和哈希一致。

### 用户体验影响

应用功能不变。版本可辨识，用户和支持人员能够确认自己运行的是哪个修复构建。

## 13. 独立实验计划

### A. 登录态快照瘦身

控制组保留完整快照；实验组逐步测试减少 `Cache`、减少非关键 `BrowserCaches` 子目录、去除持久 Backup。每个实验必须在独立测试身份下覆盖四区服、隔夜会话、2400 恢复和更新登录状态。任何回归都终止实验，不能进入正式版。

### B. 登录态加密

评估仅保护注册表认证数据、DPAPI 保护归档密钥、整包加密三种方案。验收同时包括切换耗时、崩溃恢复、旧数据升级和 Windows 用户迁移。没有可靠灾难恢复前不进入正式版。

### C. WebView2 渲染策略

保持当前禁用 GPU 为正式基线。实验版比较默认 GPU、失败后安全模式回退和减少滤镜三种方案；必须覆盖曾出现白屏的机器类型，不能只按开发机帧率决定。

## 14. 阶段验收门

每个阶段都必须满足：

- 当前阶段新增测试先失败后通过。
- `npm run lint` 无新增错误。
- `npm run build` 成功。
- C# 测试全部通过。
- `dotnet build -c Release` 成功且无新增警告。
- Git diff 只包含当前阶段文件，没有生成缓存和无关格式化。
- 使用复制的测试数据验证，禁止直接拿正式 `%LOCALAPPDATA%\KManager\Data` 做破坏性测试。
- 用户可见行为变化已列入该阶段说明；未列出的行为必须保持不变。
- 每个阶段单独提交，提交信息只描述一个交付物。

## 15. 实施计划拆分

本设计不交给实施模型一次性完成。后续必须生成以下相互独立的实施计划，并严格按顺序执行：

1. `foundation-observability-and-tests`：测试工程、路径注入、日志和现有行为特征测试。
2. `atomic-data-and-migration`：原子 JSON、备份恢复、并发锁、迁移 journal 和 staging 提交。
3. `session-transaction-and-process-control`：Battle.net 进程服务、快照 Candidate/Current/Backup 事务和失败回滚。
4. `core-bridge-and-ui-contract`：逐服务抽取、显式 bridge 接口、稳定错误码和前端一致性修复。
5. `security-ci-and-release`：导航限制、隐私文档、CI、发布校验和 `v2.0.1` 测试交付。

三个实验分别建立单独计划，不依赖主线实现，也不阻塞 `v2.0.1`：

- `session-snapshot-minimization-experiment`
- `session-state-encryption-experiment`
- `webview2-rendering-mode-experiment`

每份主线计划开始前必须确认前一份计划的测试、独立测试版和用户验收已经完成。低消耗模型一次只能接收一份计划，不得同时修改多个阶段。

## 16. 完成标准

主线优化完成时，应达到：

- JSON 损坏或写入中断不会静默显示空账号。
- 迁移可恢复、可重试、不会重复复制已完成来源，也不会删除源数据。
- 快照更新和恢复失败时保留旧可用状态，不会因为半复制继续执行。
- `BattleNetCore` 主要承担编排，数据、进程、快照和注册表职责可以独立测试。
