# KManager v2.0 Release Refresh Plan

**Goal:** Publish the latest validated source as the final v2.0 build without introducing v2.0.1. Future releases must increment the version number.

**Scope:** Rebuild the frontend and desktop client, regenerate both v2.0 artifacts, move the existing v2.0 tag to the resulting commit, and replace the existing GitHub Release assets in place.

## Tasks

1. Confirm all release metadata remains at v2.0 / 2.0.0 / 2.0.0.0.
2. Run frontend lint and production build, then synchronize `KManager-UI/out` to `KManager-Client/wwwroot`.
3. Publish the self-contained win-x64 desktop build and verify the embedded frontend and executable version.
4. Build `KManager_Setup_v2.0.exe` and `KManager-v2.0-win-x64.zip`; inspect contents, versions, hashes, and signing state.
5. Commit and push the final source, then force-update the existing `v2.0` tag as explicitly requested.
6. Replace the two assets on the existing GitHub v2.0 Release and verify the live tag, names, sizes, and digests.
7. Update `PROJECT_CONTEXT.md` with the final release state and the rule that subsequent updates increment the version.

## Verification

- `npm run lint`
- `npm run build`
- `dotnet publish KManager-Client/KManager.csproj -c Release -r win-x64 --self-contained true`
- Compare the frontend business chunk in `out`, `wwwroot`, and `publish` by SHA-256.
- Inspect the portable archive for `KManager.exe`, `wwwroot/index.html`, and the bundled WebView2 installer.
- Verify local and GitHub asset SHA-256 values match.
- Verify `origin/main`, remote `v2.0`, and the GitHub Release all resolve to the final commit/artifacts.
